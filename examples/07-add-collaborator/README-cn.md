# 邀请 Collaborator: 让别人加入你的 Repo

> 学会把同学, 老师或同事邀请进你的 repo, 让他们能真正和你一起在这个项目上工作.

## 1. 概览

这是 "Learn GitHub Basics" 系列的第七节, 它紧接着 06 节的话题往下走. 06 节你学会了 Private Repository, 也就是一个 "只有我自己能看到" 的仓库. 这很好, 但它立刻带来一个非常现实的问题: 既然除了我别人都看不到, 那当我的同学, 老师, 或者同事需要访问这个项目时, 我该怎么办?

答案就是这一节的主角: Collaborator (协作者). 你可以把特定的人一个一个地邀请进来, 让他们和你一起在这个 repo 里工作, 而对其他所有人, 这个仓库仍然是隐身的. 换句话说, collaborator 是你在 "只有我" 和 "全世界" 之间, 精确画出的那个圈子.

---

## 2. 学习目标

想象一个很具体的场景. 你把自己的课程项目设成了 private, 干净又安全. 现在到了要交作业的时候, 老师要打开你的项目批改; 或者你和一个同学要一起做 group project, 你们得在同一个 repo 里改同一批文件. 可是他们打开你的 repo URL, 看到的却是一个 404 (还记得 06 节那个匿名窗口实验吗). 对没有权限的人来说, 你的 private repo 根本不存在.

这时候唯一的入口, 就是你主动把他们邀请成 collaborator. 学会这个操作, 你才算真正打通了 "私密" 和 "协作" 这两件看起来矛盾, 实际上必须并存的事. 这是每一个真实团队每天都在做的动作.

学完这个 Task, 你将能够:

1. 用自己的话解释 collaborator 是什么, 以及被添加后默认拥有哪些权限.
2. 独立完成把一个人邀请进自己 repo 的完整操作.
3. 理解 GitHub username 的重要性: 邀请别人要用对方精确的 username, 想被别人邀请就要把自己精确的 username 告诉对方.
4. 牢牢记住一条底线: 没有邀请, 别人就无法协作.

## 4. 你将构建或学到什么

完成这一节后, 你会亲手把一个真实的人邀请进你的 repo, 并且清楚地知道对方进来之后能做什么, 不能做什么. 更重要的是, 你会建立起一个协作的基本心智: 访问权不是默认开放的, 而是你一个一个主动授予的.

---

## 5. 什么是 Collaborator

Collaborator, 就是你授权可以访问某一个特定 repo 的人.

当你把某人添加为 collaborator 之后, 在个人 repo 里, 对方默认会同时拿到两样东西:

- Read (读) 权限: 可以查看这个 repo 里的所有内容, 文件, 历史, branch, 全都能看.
- Write (写) 权限: 可以直接修改文件, 创建 branch, 提交 commit.

请特别注意第二点. Collaborator 的默认权限不是 "只能看", 而是 "也能改". 也就是说, 你一旦把某人加进来, 对方基本上就能像你自己一样在这个项目里动手了. 这不是坏事, 协作本来就需要对方能动手, 但你心里要清楚: 添加 collaborator 等于交出了一把可以改动你项目的钥匙. 所以只邀请你真正信任的人.

---

## 6. 默认是读写, 企业级还有更精细的权限

上一节说的 "默认读写", 是个人 repo 里最常见的情况. 但在更正式, 更大规模的协作里 (比如通过 GitHub Organization 管理一整个团队), 添加成员时其实有一整套更精细的权限档位可选, 让你精确控制每个人能做到哪一步. 举几个例子你就有概念了:

- 有的档位是只能看不能改, 适合外部审阅或实习旁观.
- 有的档位能改代码, 但改不了仓库的设置, 这一条尤其重要. 想想看, 如果谁都能动设置, 万一有人手一抖把你的 private repo 改成了 public (06 节讲过, 那可是不可逆的), 那就完蛋了. 把 "改内容" 和 "改设置" 的权限分开, 就是为了防这种事.

这些更高级的配置这里不展开, 你只要知道它们存在就好. 对于本课这种个人项目的场景, 记住一句话就够了: 你加进来的 collaborator, 默认是能读也能写的.

---

## 7. 先搞清楚一件事: 什么是 GitHub Username

在动手邀请之前, 有一个概念必须先弄明白, 否则你很可能加错人, 那就是 GitHub username (用户名).

username 是你注册 GitHub 时定下的那个全局唯一的标识, 它就出现在你个人主页的地址里, 形如 github.com/your-username. 全 GitHub 不会有第二个人和你的 username 完全一样. 要特别区分清楚:

- username 不是你的显示昵称 (display name). 昵称可以随便改, 可以重名, 中文英文都行, 但它不能用来邀请你.
- username 也不是你的邮箱. 邀请 collaborator 的搜索框认的是 username, 不是邮箱.

这件事有两个方向, 你都要绷着一根弦:

- 当你要邀请别人时: 你必须先拿到对方精确的 username. 一个字符都不能错, 输错了轻则找不到人, 重则把一个同名的陌生人加进了你的私密项目.
- 当你希望被别人邀请时 (比如老师或组长要把你加进他们的 repo): 你要主动, 明确地把你自己的 username 告诉对方. 别只报一个昵称, 也别只给邮箱, 要给那个 github.com/ 后面的精确字符串.

一个最稳妥的做法: 直接把你的主页 URL, 也就是 github.com/your-username, 发给对方. 这样对方复制粘贴就行, 不会因为听错或拼错而加错人.

顺便提一句, username 既然是你在 GitHub 上唯一的标识, 一开始就随手选一个顺眼, 和你名字沾点边的就好, 选定之后别老想着改. GitHub 确实允许你改它, 但真没必要折腾: username 说到底没那么金贵, 它不是你的品牌, 你将来对外打出去的名字, 和这个 username 完全可以是两码事. 至于为什么不建议乱改, 后面我们会专门用一节来讲, 这里先记住结论就行.

---

## 8. 实战: 把一个人加成 Collaborator

整个过程不到两分钟. 我们以你想邀请一位同学 John 为例.

**第一步, 进入 repo 的 Settings.** 打开你想添加协作者的那个 repo 主页. 顶部那一排标签 (Code, Issues, Pull requests 等) 的最右边, 就是齿轮图标的 Settings, 点进去.

**第二步, 找到 Collaborators.** 进入 Settings 后看左侧边栏, 在 Access 这个分类下, 有一项 Collaborators (在个人 repo 里), 点它. 如果这是你第一次进这个页面, GitHub 可能会要求你重新输入一次密码来确认身份, 这是正常的安全措施.

**第三步, 添加协作者.** 页面右侧有一个绿色的 Add people 按钮, 点它, 会弹出一个搜索框. 在这里输入对方精确的 GitHub username (还记得第 7 节说的吗, 是 username, 不是邮箱). GitHub 会列出匹配的用户, 确认头像和名字都对得上是你要找的那个人之后, 点选中, 再点 Add [用户名] to this repository.

**第四步, 就这样, 邀请发出去了.** 你会在 Collaborators 列表里看到对方, 状态是 Pending invite (等待接受).

---

## 9. 邀请发出之后: 对方接受才算数

这里有一个很多人会忽略的细节: 你点了 Add, 并不等于对方立刻就进来了.

添加之后, 对方会收到一封邀请邮件, 也可以在 GitHub 的通知里看到这个邀请. 对方必须自己点击接受 (accept), 才正式成为这个 repo 的 collaborator. 在对方接受之前, 你在 Collaborators 页面看到的一直是 Pending invite 这个等待中的状态.

所以完整的链路是: 你发出邀请, 对方收到, 对方接受, 协作才真正建立. 如果你邀请了半天对方却说自己看不到你的 repo, 十有八九是那封邀请还躺在他的邮箱里没点呢.

---

## 10. 一根要绷紧的弦: 没有邀请, 就没有协作

把 06 和 07 两节连起来, 有一条底线值得你刻在心里: 对一个 private repo 来说, 没有你的邀请, 别人就是进不来, 也协作不了.

这不是限制, 恰恰是保护. private 的默认状态就是 "只有我", 世界上没有任何人能绕过这一点自己溜进来, 唯一的入口就是你亲手发出的那张邀请. 所以每次你想让别人参与进来时, 都要主动想到这一步: 我得去 Settings 里把他加成 collaborator, 否则他连门都摸不到.

反过来说, 这也意味着安全的主动权完全在你手里. 谁能进, 谁不能进, 什么时候把谁移出去, 全由你一个人说了算.

这根弦你现在也许还用不上, 但它迟早会用上. 也许是将来你的导师帮你改论文, 需要进你的 repo 直接动手; 也许是你带的学生, 或者你的同学, 要和你一起做一个东西. 到那个真正需要协作的时刻, 你脑子里要能立刻闪过这个念头: 对方进得来吗? 我把他加成 collaborator 了没有? 如果没加, 他就还在门外, 你得先去 Settings 里把他请进来. 把这个反射先建立起来, 其实比现在马上拉个人来演练一遍更重要, 所以这一节我们不特意安排动手练习: 你把上面添加协作者的流程看懂, 记在心里, 等真需要的那天, 自然就用得上了.

---

## 11. 回顾: 我们学到了什么

- Collaborator 是你邀请进某个 repo 的人, 它让 private repo 也能实现协作.
- 在个人 repo 里, collaborator 默认同时有 Read 和 Write 权限, 也就是对方能看也能改.
- 更大规模的协作 (如 Organization) 里还有更精细的权限档位, 比如只读, 或能改代码但改不了设置, 本课不展开.
- 邀请认的是精确的 GitHub username, 不是昵称也不是邮箱; 想被邀请就把自己的 username 或主页 URL 清楚地告诉对方.
- 添加路径: repo, Settings, 左侧 Access 下的 Collaborators, Add people.
- 邀请要对方接受才生效, 接受前一直是 Pending invite.
- 底线: 对 private repo, 没有邀请, 别人就无法访问, 也无法协作.

---

## 12. 导师寄语

**为什么这件事重要:**

添加 collaborator 这个操作本身很简单, 但它背后藏着一个重要的职场道理: 协作的基础是信任, 而信任是通过权限来体现的. 当你把某人加成 collaborator, 你其实是在说, 我信任你, 愿意让你进入我的项目空间, 甚至改动我的东西. 这就是为什么我反复强调, 只邀请你真正信任的人, 也反复强调要用精确的 username, 别把钥匙递错了人.

**关键洞见:**

- 权限管理是一门分寸的学问. 给得太少, 别人无法有效参与; 给得太多, 就可能带来不必要的风险. Collaborator 的读写权限, 是应对大多数学习和小团队场景的一个简单而够用的起点.
- 访问权默认是关着的, 这是好事. 它意味着安全的主动权始终在你手里, 你不主动开门, 谁都进不来.
- username 是协作世界里你的精确坐标. 记不住别人昵称没关系, 但一定要给对方一个不会认错的 username 或主页链接.

**下一步:**

把这个习惯带进你真实的协作里. 下次要和别人一起做项目, 第一件事就是想清楚: 谁需要进来, 我有没有他精确的 username, 我把他加进去了没有. 随着你参与更大的项目, 你会接触到 Organization, Team, Branch Protection 这些更精细的协作机制. 其中 Organization 是最常撞上的一个, 10 节会专门讲它是什么, 以及别人分享给你的仓库为什么该去那里找. 但今天你已经掌握了最根本的第一步, 学会把对的人请进你的项目.

---

## 13. 速查

**Collaborator 是什么:** 你邀请进某个 repo 的人, 个人 repo 里默认拥有 Read 加 Write, 也就是能看也能改.

**添加路径:** repo, Settings, 左侧 Access 下的 Collaborators, 绿色的 Add people 按钮.

**认的是 username:** 搜索框输入对方精确的 GitHub username, 不是昵称, 不是邮箱. 最稳妥是让对方把自己的主页链接 github.com/USERNAME 发给你.

**要对方接受:** 添加后对方收到邀请邮件, 接受前状态是 Pending invite, 接受后才正式生效.

**底线:** 对 private repo, 没有你的邀请, 别人无法访问, 也无法协作.
