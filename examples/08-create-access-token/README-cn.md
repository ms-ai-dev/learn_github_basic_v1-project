# 生成你的 GitHub Personal Access Token: 给机器用的通行证

> 生成一个专门给程序使用的身份凭证, 理解它为什么比直接把密码交出去安全得多.

## 1. 概览

这是 "Learn GitHub Basics" 系列的第八节. 前面几节你都是以 "一个人" 的身份, 在浏览器里点来点去地操作 GitHub. 这一节我们换一个视角: 当一个程序要替你操作 GitHub 时, 它怎么证明 "我是代表你来的"? 答案就是 Personal Access Token.

要先说清楚一件事: 这是一项通用的 GitHub 技能, 和你具体拿它去做什么项目没有关系. 无论你以后是用命令行推代码, 用第三方工具管理仓库, 还是让某个自动化脚本替你干活, 背后都是同一个东西在证明你的身份. 学会它, 你就掌握了 GitHub 从 "网页点点点" 通往 "程序自动化" 的那把钥匙.

再给你打个预防针: 你现在并不会立刻就用到它. 这一节更像是先在你脑子里埋下一个常驻的概念, 你只要知道有 token 这么个东西就好. 但请把它记住, 因为后面很多地方都会用到, 尤其是当你操作 private repo 的时候.

---

## 2. 学习目标

先铺一个你以前可能没意识到的事实: 你在 GitHub 网页上能点的每一个按钮, 程序都能做. 你点 Create repository 建一个仓库, 一条命令就能做到同样的事; 你点 Import repository 导入项目, GitHub 后台也是走同一套接口帮你完成的. 正因为 GitHub 的每个功能都开放了对应的程序接口, 你才能用命令行, 用工具, 用脚本去操作它.

那么问题来了: 你在网页上是靠密码登录一次, 浏览器就记住了你. 可一个程序没有浏览器, 也没有你的登录状态, 它拿什么证明身份? 最直觉的想法是把密码给它用, 而这恰恰是危险的开始. 这一节就是要给这个问题一个安全的答案.

学完这个 Task, 你将能够:

1. 用自己的话说清 Personal Access Token 是什么, 以及它和密码的根本区别.
2. 独立生成一个权限最小 (只有 repo) 的 classic token.
3. 用密码管理器安全地保存它, 并知道它随时可以撤销和重建.
4. 认得这个东西的各种叫法 (PAT, GitHub token, auth token), 知道它们指的是同一样东西.

- 最好手头有一个密码管理器 (1Password, Bitwarden, 或浏览器自带的都行), 用来安全保存 token.
- 本节全程纯网页操作, 不需要命令行, 也不区分 Mac 还是 Windows, 步骤完全一样.

## 4. 你将构建或学到什么

完成这一节后, 你会亲手生成一个真实可用的 GitHub token, 把它安全地存进密码管理器, 并且清楚地知道它是什么, 该怎么保管, 以及万一出事怎么一键止损. 这是你以后一切自动化操作的起点.

## 5. 核心类比: token 是给机器用的密码

理解 token, 先记住一句话: 密码是给你这个活人用的, token 是给机器用的.

当你本人在浏览器里操作 GitHub, 你输一次密码登录, 就证明了 "我是我". 但当一个程序 (命令行 Git, 一个开发工具, 一段自动化脚本) 要替你去操作 GitHub 时, 它面前没有浏览器, 也没有你登录后的状态, 它同样需要一样东西来证明 "我是代替某某来的, 请放行". 这个专门发给程序用的凭证, 就是 Personal Access Token.

所以你完全可以把 token 想成一个 "机器专用的密码": 作用和密码类似, 都能证明身份, 让 GitHub 放行; 但它是发给程序的, 不是发给人的. 而正因为使用者是程序不是人, 它在设计上比密码要灵活, 也安全得多. 下面就来看它好在哪.

---

## 6. 为什么不直接用密码, 以及 token 好在哪

最直觉的想法是: 把我的 GitHub 密码直接给程序用不就行了? 这非常危险, 原因一句话就能概括: 密码权力太大, 而且出事没法局部止损.

你的 GitHub 密码几乎能做一切事: 删仓库, 改邮箱, 注销账号, 操作你加入的所有 organization. 把它交给一个工具, 等于把你家的万能钥匙给了别人, 每扇门都对它敞开. 更糟的是, 万一某个工具把你的密码泄露了, 你唯一的补救就是改密码; 可你一改, 其他正常在用这个密码的工具也全部失效, 得一个个重新配置.

Token 就是为了解决这些而生的, 它有三个密码给不了的好处:

- 权限可以缩小. 生成时你可以只给它 "读写仓库" 的权限, 不给删仓库, 不给管理 organization, 不给改账号. 就算它泄露了, 别人拿着也做不了多少事. 它只是一张 "只能开特定房间的门卡", 不是万能钥匙.
- 可以随时单独撤销, 互不影响. 你可以同时发好几个 token 给不同程序用, 哪个出问题就一键删哪个, 其余 token 和你的密码毫发无伤.
- 可以设过期时间. 让它 30 天或 90 天后自动失效, 就算你忘了手动撤销, 到期它也自动变成一张废纸.

这里藏着 token 最关键的一层价值: 隔离. 你对比一下两种 "丢失". 密码丢了, 别人可能连你的账号本身都能夺走, 你就彻底失去这个账号; 而 token 丢了, 你的账号还是你的, 别人顶多在你撤销它之前访问到它授权范围内的那点数据, 你一撤销, 立刻止损. Token 把 "账号的所有权" 和 "对数据的访问权" 这两件事分开了, 这就是它比密码安全得多的根本原因.

补一个事实: 正因为密码太万能, GitHub 从 2021 年 8 月起已经彻底禁止用登录密码做命令行 Git 操作和 API 调用, 程序化操作只能用 token. 换句话说, 这不是一个可选项, 而是你迟早都要走的一步.

---

## 7. token 还干一件事: 证明你是你

到这里我们一直把 token 说成 "给机器用的密码", 它管的是 "你能做什么", 也就是权限. 但 token 其实还悄悄干着另一件事: 证明 "你是你", 也就是身份. 这两件事听起来像一回事, 其实是两回事, 值得单独拎出来说一下.

举个大学里的例子你就懂了. 开学时, 老师要把一份资料的访问权发给你, 他得先知道你是谁, 于是你把自己的 GitHub username 告诉他. 但 username 这东西是半公开的, 你告诉了老师, 也可能被同学看到, 或者被写进某份名单. 问题就来了: 既然别人也知道你的 username, 那别人是不是可以冒充你, 跑去跟老师说 "我就是这个 username"?

光凭 username 确实防不住冒充, 因为它只是一个 "名字", 谁都能报. 但有一样东西别人冒充不了, 那就是 token. 只有真正的你, 手里才握着那串只属于你的 token; 谁能拿出这串 token, 谁就能被验证 "的确是本人". 名字谁都能喊, 但那串秘密的凭证只有你有.

所以请记住这个区分: "你是你" (身份) 和 "你有权限" (授权) 是两码事. 你可能确实是你, 却没有某个仓库的权限; 也可能有权限, 但得先证明你是你. token 巧妙的地方在于, 它把这两件事合在了一根字符串里, 既能证明你是谁, 又能界定你能干什么.

这一层你现在先知道有这么回事就好, 不用深究. 我们借大学发资料这个小例子, 只是想让你对 "一串凭证既代表身份, 也代表权限" 有个直觉. 以后真遇到需要 "证明你是你" 的场景, 你自然就能举一反三.

---

## 8. 统一一下叫法: 它有好几个名字

你在不同地方会看到这个东西被叫成好几个名字, 别被绕晕, 它们说的都是同一样东西:

- Personal Access Token, 简称 PAT, 这是它的正式全名.
- GitHub token, 或者干脆就叫 token, 是最口语的叫法.
- auth token (authentication token), 强调它是用来 "认证身份" 的.

以后无论在本课还是别的教程里, 只要冒出这几个词, 你脑子里对应的就是这一节要生成的这串东西.

另外顺带一提, GitHub 的 token 其实有两种. 一种是较新的 fine-grained token, 能把权限精确控制到单个仓库, 但设置步骤多, 概念也复杂; 另一种是经典的 Tokens (classic), 权限粗一些, 但简单直接. 本节我们用 classic, 因为它更好上手, 对新手也更友好.

---

## 9. 动手生成一个 classic token

整个过程纯网页完成, Mac 和 Windows 一模一样, 也不用碰命令行.

**第一步, 进入 Settings.** 点右上角你的头像, 在下拉菜单里点 Settings.

**第二步, 找到 Developer settings.** 把左侧边栏一直往下拉, 拉到最底部, 点 Developer settings. 它藏得比较深, 是因为 token 算一种开发者工具, 但别被名字吓到, 你不用是开发者也能用. 嫌一层层找麻烦, 可以直接在地址栏敲 github.com/settings/tokens 一步到位.

**第三步, 选类型.** 在 Personal access tokens 下面选 Tokens (classic).

**第四步, 开始生成.** 右上角点 Generate new token, 再选 Generate new token (classic). 这时 GitHub 可能要你再输一次登录密码确认是本人, 这是正常的安全措施, 毕竟你正在造一张通行证.

**第五步, 填信息.** 这一屏有三个关键字段:

- Note (备注): 给这个 token 起个能认出用途的名字, 比如 my-learning-token. 它只是给你自己看的标签, 不影响功能.
- Expiration (过期时间): 设一个有效期. 学习用选 90 days 就挺合适. 列表里也有 No expiration (永不过期), 图省事的话能选, 但我不建议你养成这个习惯, 给凭证设期限本身就是一种好习惯.
- Select scopes (权限范围): 这是最重要的一步, 只勾 repo 这一项就够了. 勾上它之后, 它下面一串子权限会自动跟着勾上, 这是正常的. 其他所有权限一律别碰.

**第六步, 生成.** 拉到页面底部, 点绿色的 Generate token.

---

## 10. 只显示一次, 立刻用密码管理器保存

生成后, 页面上会出现一串以 ghp_ 开头的字符串, 这就是你的 token.

最要命的一点: 这串东西只显示这一次. 你一旦刷新或离开这个页面, 它就再也看不到了. GitHub 不保存明文, 你没法 "找回" 它, 只能重新生成一个新的. 所以现在, 立刻做两件事:

1. 点 token 旁边的复制图标, 把它复制下来.
2. 打开你的密码管理器 (1Password, Bitwarden, 或浏览器自带的都行), 新建一条记录: 名称写 GitHub Personal Access Token, 密码栏粘贴这串 token, 备注里记上它的权限 (repo) 和创建日期.

千万别把它贴到聊天记录, 记事本, 或者桌面的一个 txt 里. Token 和密码一样敏感, 任何能看到那些地方的人都能拿它访问你的仓库. 密码管理器会加密存储, 要主密码才能看, 安全级别高得多.

---

## 11. 随时可撤销: 感受 token 的可丢弃

最后, 要让你亲身记住 token 和密码最不一样的那一点: token 是可以随手扔掉的.

你随时可以回到 github.com/settings/tokens, 在列表里找到任何一个 token, 点 Delete 把它作废. 作废之后, 正在用这个 token 的程序会立刻失去访问, 但你的账号, 密码, 仓库, 登录状态, 全都毫发无损. 需要了再生成一个新的就行, 想建几个建几个, 想删哪个删哪个.

把这件事和 "改密码" 对比一下你就懂了: 改密码是件大事, 牵一发动全身, 一动其他地方全得跟着重配; 而作废一个 token 只是关掉一扇特定的门, 轻描淡写, 毫无心理负担. 这种 "可丢弃", 正是 token 存在的意义.

## 12. 练习

### 练习 1: 生成并安全保存一个 token

**目标:** 独立生成一个只有 repo 权限的 classic token, 并把它妥善保存起来.

**怎么做:**

1. 在地址栏直接敲 github.com/settings/tokens, 进入 Tokens (classic) 页面.
2. 点 Generate new token, 选 Generate new token (classic), 按提示输密码确认身份.
3. Note 填一个能认出用途的名字 (比如 my-learning-token); Expiration 选 90 days.
4. Select scopes 里只勾 repo 这一项, 其他一律不勾.
5. 拉到底点 Generate token, 立刻复制那串以 ghp_ 开头的字符串.
6. 把它存进你的密码管理器, 记上权限 (repo) 和日期.

**你会观察到:**

那串 ghp_ 开头的 token 只出现这一次, 刷新页面就没了. 存进密码管理器之后, 你就有了一个安全, 随取随用的凭证.

> **关键洞见:** 给的权限刚好够用就好, 多勾一项就多一分风险. 只勾 repo, 就是把万一泄露时的爆炸半径压到最小.

### 练习 2 (可选, 强烈推荐): 撤销它, 感受和密码的不同

**目标:** 亲手作废一个 token, 用身体记住它和密码的根本区别.

**怎么做:**

1. 回到 github.com/settings/tokens.
2. 如果你担心删掉练习 1 那个会心疼, 可以先随手再生成一个专门用来练删的.
3. 在列表里选中一个 token, 点 Delete, 按提示确认.
4. 删完之后, 特意去看一眼: 你的账号, 你的仓库, 你的登录状态, 有没有任何变化.

**你会观察到:**

token 从列表里消失了, 但你的账号一切如常, 你甚至没有被登出. 如果刚才有程序在用这个 token, 那个程序会失效, 仅此而已, 换一个新 token 就能恢复.

> **关键洞见:** 撤销 token 毫无心理负担, 因为它只碰得到 "数据访问", 碰不到 "账号所有权". 密码你可不敢这么随手作废. 这就是隔离的价值, 你刚刚亲手验证了一遍.

## 13. 回顾: 我们学到了什么

- 密码是给你这个活人用的, token 是给机器用的, 两者作用相似但对象不同.
- 直接把密码给程序很危险: 密码权力太大, 泄露了还没法局部止损.
- Token 的三个好处: 权限可缩小, 可单独撤销, 可设过期时间.
- Token 最关键的价值是隔离: 它把 "账号所有权" 和 "数据访问权" 分开, 丢了 token 也不至于丢账号.
- Token 不只界定 "你能做什么" (权限), 也能证明 "你是你" (身份); 名字谁都能报, 但那串凭证只有你有.
- PAT, GitHub token, auth token 说的都是同一样东西; 本课用简单的 Tokens (classic).
- 生成时只勾 repo, 遵循最小权限原则; token 只显示一次, 必须立刻复制并用密码管理器保存.
- Token 随时可以一键撤销和重建, 这正是它区别于密码, 也比密码安全的地方.

---

## 14. 导师寄语

**为什么这件事重要:**

你可能觉得今天只是 "生成了一个 token", 操作不到五分钟. 但这背后是一个在信息安全领域极其重要, 也会让你受用一生的思维: 最小权限原则 (Principle of Least Privilege). 我们明明可以把所有权限都勾上一劳永逸, 为什么只勾 repo? 因为每多一项权限, 就多一分风险. 权限给得刚好够用, 不多给一分, 出事时的爆炸半径就最小.

**关键洞见:**

- 这个原则在职场里无处不在: 数据库账号只给应用需要的那几张表, 云服务的 key 只授权特定服务, 新员工只拿到干活必需的权限. 不是不信任你, 而是权限越小, 出错时的代价越小.
- 好的安全习惯不是 "出事了再补救", 而是 "从一开始就把风险圈在最小范围内". Token 的可撤销, 可过期, 可缩权, 就是把这个思路做进了工具里.
- 凭证存哪里和给多大权限一样重要: 永远用密码管理器, 永远不要明文乱放.

**下一步:**

以后每当你要创建 token, API key, 或任何形式的凭证时, 都先问自己两个问题: 这次操作到底需要哪些权限 (只勾必要的), 以及这个凭证该存在哪里 (永远用密码管理器). 安全事故往往不是因为黑客太厉害, 而是因为有人给了远超需要的权限, 或者把凭证贴在了不该贴的地方. 养成这两个习惯的人, 在任何团队里都会被信任.

## 15. 速查

**它是什么:** 给机器用的 "密码", 用于浏览器登录之外的认证场景 (命令行 Git, API, 各种开发工具).

**几种叫法:** Personal Access Token (PAT), GitHub token, auth token, 指的都是同一样东西.

**生成入口:** 地址栏直接敲 github.com/settings/tokens, 选 Tokens (classic), Generate new token (classic).

**关键设置:** Note 起个能认出用途的名字; Expiration 选 90 days; Select scopes 只勾 repo.

**保存:** token 以 ghp_ 开头, 只显示一次, 立刻复制并存进密码管理器, 绝不明文乱放.

**止损:** 回到 github.com/settings/tokens 一键 Delete 即可撤销, 账号本身毫发无损.
