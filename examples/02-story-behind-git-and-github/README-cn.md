# Git 与 GitHub 的来历: 两段故事, 和一个不只属于技术人的舞台

> 这一节不动手, 只讲背景. 搞清楚 Git 和 GitHub 分别是什么, 各自怎么来的, GitHub 为什么愿意免费给你一块地方, 以及为什么这块地方不是程序员的专属.

## 1. 概览

后面每一节你都会动手: 建 repo, 改文件, 开分支, 邀请人, 装桌面工具. 这一节不一样, 它不要求你点任何按钮.

原因有三个.

**第一, 你即将天天使用两个名字非常像的东西: Git 和 GitHub.** 绝大多数人从来没弄清它们的区别, 用了好几年也说不上来. 这不影响你点按钮, 但会影响你的判断: 出问题时不知道该怪谁, 换工具时不知道什么能带走, 别人聊起来时也接不上话.

**第二, GitHub 是一家公司的产品, 却愿意让你免费存无限多的项目**, 免费给你的网站提供托管, 免费让你和别人协作. 这事听着不太对劲. 想清楚它为什么慷慨, 你才知道这份慷慨能不能靠得住, 该用到什么程度.

**第三, 也是最容易被忽略的一条: 你多半以为这是程序员的地方.** 打开 GitHub 满眼都是代码, 这个印象太自然了. 但它其实是这门课最想帮你破掉的一个误解. GitHub 的底子是 "作品加社交", 不是 "代码加社交", 而一个能长期存放作品, 又自带社交的地方, 对任何想让别人看见自己做过什么的人都成立, 跟你写不写代码没关系. 这条线会一路贯穿这门课, 现在先把它立住.

这一节就讲这几件事: 两段故事, 一笔账, 和一个立场.

---

## 2. 学习目标

先说两个很常见的尴尬场景.

一个是: 有人问你 "你会 Git 吗", 你说会; 又问 "那 GitHub 呢", 你也说会. 再问 "它俩什么关系", 你就卡住了. 或者反过来, 有人告诉你 "公司不用 GitHub, 用 GitLab", 你心里一沉, 以为要重学一遍.

另一个是: 你不是搞技术的, 有人建议你 "把东西放 GitHub 上", 你第一反应是 "那不是程序员用的吗, 我放上去合适吗". 于是你继续把方案存在本地文件夹里, 简历改到第七版还叫 resume-final-v3, 而你这些年做过的东西, 除了你自己没人看得见.

这两种卡壳来自同一个空白: 没人跟你讲过这两个东西各自是什么, 以及这个平台的本质到底是什么. 补上这个空白, 你后面学的每一个操作都会落在一张清楚的地图上, 而不是一堆孤立的按钮.

学完这个 Task, 你将能够:

1. 讲清 Git 是怎么来的, 它当初要解决的是什么问题.
2. 讲清 GitHub 是怎么来的, 它在 Git 之上多做了什么.
3. 一句话说明白 Git 和 GitHub 的区别与关系, 并知道换一个平台意味着什么.
4. 说清 GitHub 为什么敢给你这么多免费额度, 以及你该怎么用好这份慷慨.
5. 说清为什么 GitHub 那套作品加社交的构造对不写代码的人同样成立, 以及它凭什么能当作品和职场的敲门砖.

## 5. Git 的故事: 一场翻脸逼出来的工具

2005 年之前, Linux kernel 是全世界最大的开源项目之一, 上千个开发者往里提交代码. 管理这么多人的改动需要一个版本控制系统, 当时他们用的是一个叫 BitKeeper 的商业软件, 厂商出于好意, 允许 kernel 社区免费使用.

2005 年, 这份好意没了. 厂商和社区闹翻, 收回了免费授权. 一夜之间, 全世界最重要的开源项目失去了管理代码的工具.

Linux 的创始人 Linus Torvalds 的反应很有代表性: 他没有去找替代品, 而是自己动手写了一个. 从动手到这个新工具能够管理自己的源码, 只隔了几天. 这个工具就是 Git.

Git 在诞生之初就被三条硬要求逼着长成了今天的样子:

- **要快.** kernel 的代码量巨大, 一个操作要是等半分钟, 上千个开发者每天就是在集体浪费生命.
- **要分布式.** 不能有一台中心服务器说了算, 每个人的电脑上都得有完整的历史.
- **要能防篡改.** 开源项目谁都能提交, 所以每一次改动都要有办法校验它没被人偷偷动过手脚.

顺带一提这个名字. Linus 有自嘲的习惯, 他说自己写的项目都以自己命名, 而 git 在英式英语里是 "讨厌鬼" 的意思. 一个改变了整个行业的工具, 名字是它作者骂自己的一句话. 写出来几个月后他就把维护权交给了 Junio Hamano, 由后者一直维护到今天.

这段故事里有一个细节值得你记住: **Git 从头到尾只关心文本, 它根本不知道自己管的是不是代码.** 它眼里只有一行一行的字, 谁在什么时候改了哪一行. 这一点后面会派上大用场.

---

## 6. Git 到底解决了什么: 每个人手里都有一份完整历史

Git 之前的主流工具是集中式的: 项目的历史只存在于一台中心服务器上, 你的电脑里只有当前这一版文件. 想看历史要联网问服务器, 想开一条分支要在服务器上开, 服务器挂了大家一起停工.

Git 把这件事彻底翻了过来: 当你把一个项目 clone 到本地, 你拿到的不是最新的那一版文件, 而是**这个项目从第一天起的完整历史**. 于是:

- 断网也能干活. 提交, 看历史, 切分支, 全都在本地完成, 什么时候联网什么时候同步.
- 分支变得极其便宜. 开一条新分支不需要惊动任何服务器, 也不需要复制一份代码, 所以你可以随便开, 随便扔.
- 备份是自动的. 每一个 clone 都是一份完整副本, 参与的人越多, 这个项目越难被抹掉.

这三点你后面都会亲身体验到: 分支那一节你会开一条分支去做实验, 桌面工具那一节你会清楚地看到 "本地" 和 "远程" 是两个地方, 而这两件事的根都在这里.

## 7. GitHub 的故事: 给一个命令行工具建了一个广场

Git 很强, 但它有一个很现实的问题: 它是一个命令行工具, 而且只管你自己电脑上的那份历史. 两个人想一起干活, 得自己想办法把仓库放到某台大家都能访问的机器上, 还得自己配好权限. 在 2008 年, 这件事足以劝退绝大多数人.

2008 年, 几个开发者 (Tom Preston-Werner, Chris Wanstrath, PJ Hyett, Scott Chacon) 做了一个网站, 叫 GitHub. 它做的事听起来平平无奇: 帮你把 Git 仓库放在网上. 但他们多做了一件真正改变格局的事, 就是**把社交属性装了上去**.

在 GitHub 上, 一个仓库不只是一堆文件, 它有主页, 有 README 当门面, 有 star 表示别人的认可, 有 fork 让别人拿走一份, 有 issue 供人讨论, 有关注它的人. 你自己也有一个主页, 上面挂着你做过的所有东西, 还有一整年的贡献记录. 你可以 follow 一个人, 也可以被人 follow.

请留意这一串东西的性质: 主页, 门面, 认可, 关注, 讨论, 时间线. **这套构造和代码没有半点关系, 它是一个作品展示与社交的构造**, 只不过它最早服务的那批人恰好在写代码. 这就是第 10 节要展开的那件事, 先按下不表.

其中最关键的一个发明是 Pull Request. 注意, PR 不是 Git 的功能, 而是 GitHub 造出来的产品概念: 把 "我改好了, 请你看看要不要合并" 这件原本靠邮件来回沟通的事, 变成了网页上一个人人都会用的按钮, 还顺手带上了讨论区和改动对比. 今天全世界的团队协作几乎都建立在这个流程上, 而你会在后面专门学它.

于是 Git 从一个工具变成了一个广场. 开源项目从散落在各处的网站集中到了同一个地方, 找项目, 看作品, 提改动, 全在一处完成. 到 2018 年, Microsoft 用 75 亿美元把 GitHub 买了下来, 这个价格买的其实不是那些代码, 而是全世界的人都在这儿这件事.

---

## 8. Git 不等于 GitHub, 这是最值得记住的一条区别

现在可以把两者摆在一起了:

- **Git 是一个版本控制工具**, 装在你自己电脑上, 免费, 开源, 不属于任何公司. 它负责记录每一次改动, 管理分支, 合并内容. 就算断网, 就算全世界的托管网站都关门, 它照样能用.
- **GitHub 是一个托管 Git 仓库的网站**, 属于一家公司. 它负责把你的仓库放在网上, 给它一个地址, 管理谁能看谁能改, 再加上 PR, issue, 主页, star, 贡献图这些 Git 本身没有的东西.

一句话: **Git 管的是历史, GitHub 管的是这份历史放在哪, 谁能围着它一起工作, 以及别人怎么看见它.**

同类的托管网站不止 GitHub 一家, 常见的还有 GitLab, Bitbucket, Codeberg. 它们底下跑的都是同一个 Git. 这带来一个很让人安心的结论: 你在 GitHub 上积累的项目历史是可移植的. 只要你在本地 clone 过一份, 你手里就是完整的历史, 换一个平台推上去就行, 没有人能把你锁死.

所以 "公司不用 GitHub 用 GitLab" 这句话, 需要你重学的东西其实很少. 你在这门课里学到的 commit, branch, merge, PR 这套心智, 换个网站照样成立, 变的只是按钮的位置和颜色.

## 9. GitHub 凭什么这么慷慨

现在说那笔听起来不太对劲的账. 一个免费账号能从 GitHub 拿到的东西大致是这样:

- 想建多少个仓库就建多少个, public 和 private 都不限量.
- private 仓库也能免费邀请协作者, 不用为了省钱把私事公开.
- 免费的自动化额度, 让 GitHub 在你每次提交之后自动帮你跑点东西.
- 免费的静态网站托管, 你可以直接把一个仓库变成一个能对外访问的网页.
- 面向学生和教师的一整套教育优惠, 以及对开源维护者的额外照顾.

具体额度年年在变, 不用背, 需要时去官网看一眼就好. 值得想清楚的是另一个问题: 一家公司为什么愿意这么做?

答案不是慈善, 是一笔算得很清楚的账:

- **人是入口.** 个人用得爽, 将来他进了公司, 大概率会推荐公司买 GitHub 的企业版. 真正掏钱的是企业, 不是你.
- **人多本身就是护城河.** 全世界的项目都在这里, 你才不得不来这里; 你来了, 又让下一个人更不得不来. 免费额度是维持这个循环最便宜的手段.
- **公开的内容对平台有价值.** 你放上去的公开作品让这个广场更热闹, 也成了别人搜索和学习的素材. 你不是白拿, 你也在贡献.
- **背后是云生意.** Microsoft 收购它, 图的是从做东西到发布上线这条链路, 而这条链路的终点是卖云服务.

所以这份慷慨是可持续的, 你可以放心用. 但也正因为它是一笔生意而不是一份承诺, 有两条边界值得记住: 一是**别把 GitHub 当成唯一的副本**, 本地 clone 一份, 或者在别的平台留一份镜像, 成本几乎为零; 二是**免费档的规则会变**, 依赖它的时候心里有数就好.

## 10. 这块舞台不只属于技术人

现在回到第 1 节埋下的那条线, 也是这一节真正想让你带走的东西.

**先承认那个印象从哪来.** 你打开 GitHub, 首页推的是开源项目, 点进去满屏代码, 讨论区里全是术语. 得出 "这是程序员的地方" 这个结论一点都不奇怪. 很多不搞技术的人就是在这一步转身走了.

**但把这个平台拆开看, 它给你的其实是两样东西.**

一样是**作品有地方放**: 一个 repo 就是一个作品的家, README 是它的门面, 每一次修改都留下时间戳和说明, 谁在什么时候改了什么, 清清楚楚. 第 5 节说过, Git 眼里只有文本, 它根本不知道自己管的是不是代码. 而绝大多数职业的产出, 剥到最里面都是文本: 文案与活动方案, 调研报告, 教案与讲义, 剧本与书稿, 数据分析的结论, 产品需求, 甚至一份反复修订的简历.

另一样是**这个地方自带社交**: 主页是你的门面, star 是别人的认可, follow 是持续的关注, issue 是公开的讨论, 贡献图是一条谁也伪造不了的时间线. 这套东西没有一件是代码专属的.

**把这两样合起来, 就是敲门砖.** 你想让别人相信你能做事, 最缺的从来不是形容词, 而是证据. 简历上写 "擅长活动策划" 是你自己说的一句话; 而一个 public repo 是可以点进去看的东西: 你做过哪几场, 每一版方案怎么改的, 复盘写了什么, 从什么时候做到什么时候. 前者是声明, 后者是证据. 在一个人人都能让 AI 生成漂亮说辞的年代, 能点进去看过程的东西, 分量只会越来越重.

而且在很多非技术行业里, 这甚至是一种降维打击: 别人递过来一个 PDF 附件, 你递过去一个链接, 里面有完整的作品和它长出来的全过程. 这不是你比谁厉害, 只是你用的工具更适合留下证据.

几个具体的样子, 帮你把这件事落地:

- 一个做市场的人, 每场 campaign 一个目录, 方案, 素材清单, 投放数据, 事后复盘各一份, 一年下来就是一部能翻的作品集.
- 一位老师, 把课件和教案版本化, 每学期改了什么一目了然, 换学校时整套东西跟着走.
- 一个写东西的人, 把每一稿都留痕, 编辑问 "上一版那句话呢", 翻一下就找回来了.
- 一个想转行的人, 把学习笔记和练习摊开在公开仓库里, 面试时不用解释自己有多努力, 让对方自己去看那一年的记录.

**也说两句诚实话.** GitHub 最擅长的是文本和它的演变过程, 不是大文件. 视频, 高清设计稿, 大堆原始素材放上去能放, 但它管不好, 那些东西更适合放在别处, 在 repo 里留一个链接和说明就行. 另外, 公开是有边界的, 涉及雇主的内部资料, 客户隐私, 或者你还不想让人看到的半成品, 该 private 就 private, 后面专门有一节讲这条线.

所以这一节的立场很明确: **你有资格站在这块舞台上, 不需要先成为程序员.** 至于具体怎么把日常工作搬上来并养成习惯, 后面 07 节会手把手带你做一遍.

## 11. 那你该怎么用这块免费的舞台

把上面这笔账和这个立场落到你自己身上, 有三件事值得现在就想清楚.

**第一, 把它当成默认的工作区, 而不是交作业的地方.** 既然存多少都不要钱, 那笔记, 作业, 方案, 简历草稿, 读书摘要, 全都可以放进来. 关键不在于你做的是哪一行, 而在于你是不是需要留下记录.

**第二, 能公开的尽量公开.** public 仓库不占你任何额度, 却能变成别人看得见的作品集. 一个陌生人想了解你, 点开你的主页就能看到你在做什么, 做了多久. 这是免费档里最值钱的一部分, 也是上一节说的那块敲门砖真正生效的地方.

**第三, 分清什么绝对不能公开.** 慷慨的另一面是公开的东西传播极快且收不回来. 密码, 密钥, 客户资料, 公司内部文件这些东西该放 private 就放 private. 后面讲 private repo 那一节会把这条红线讲透.

## 12. 练习

这一节不需要你创建或改动任何东西, 三个练习都是打开来看一眼, 建立感觉就够了.

### 练习 1: 用一句话复述 Git 的来历

**目标:** 把这段故事真正装进自己的话里, 而不是看过就忘.

**怎么做:**

1. 合上这一页.
2. 用一句话对自己 (或者随便找个人) 说清楚: Git 是谁写的, 为什么写, 它最特别的地方是什么.
3. 再打开这一页对照第 5, 6 节, 看看漏了哪一点.

**你会观察到:**

大多数人第一次复述会漏掉 "分布式" 这一条, 只记得 "Linus 写的". 而恰恰是分布式那一条, 决定了你后面用起来的手感.

> **关键洞见:** 能用自己的话讲出来, 才算真的知道; 复述不出来的部分, 就是你其实没看懂的部分.

### 练习 2: 去看一眼免费档到底给了什么

**目标:** 对 GitHub 的慷慨有一个具体的, 而不是模糊的认识.

**怎么做:**

1. 打开 github.com 的 Pricing 页面.
2. 只看 Free 那一档, 逐条扫一遍它列出来的东西.
3. 挑出一条你之前完全不知道自己能免费用的, 记下来.

**你会观察到:**

免费档给的东西比大多数人以为的多得多. 很多人用了好几年 GitHub, 只用过 "存代码" 这一项功能.

> **关键洞见:** 白给的东西不去了解, 等于没有.

### 练习 3: 找一个一行代码都没有的仓库

**目标:** 亲眼确认这个广场上站着的不只是程序员.

**怎么做:**

1. 用 GitHub 顶部的搜索框搜一个非代码类的关键字, 比如 `awesome`, `handbook`, `notes`, `book`, `curriculum`, 再把结果按 star 排一下序.
2. 挑一个点进去, 看它的 README, 文件列表, star 数, 以及有多少人参与过.
3. 再点进 Pull requests 标签, 随便打开一个, 看看一次改动是怎么被讨论和合并的.
4. 顺手点开这个仓库某个贡献者的主页, 看一眼他的贡献图.

**你会观察到:**

有大量高 star 的仓库里一行代码都没有, 它们是清单, 手册, 笔记, 教程, 甚至整本书. 而它们用的展示方式和协作流程, 和那些代码项目一模一样.

> **关键洞见:** 这个广场认的是 "你做了东西并且留下了记录", 不是 "你写的是不是代码".

---

## 13. 回顾: 我们学到了什么

- Git 诞生于 2005 年, 是 Linux kernel 社区失去原有工具之后, Linus Torvalds 亲手写出来的, 目标是快, 分布式, 可校验.
- Git 最根本的特点是分布式: 每个 clone 都带着完整历史, 所以断网能干活, 分支很便宜, 备份是天然的. 而且它眼里只有文本, 不关心那是不是代码.
- GitHub 诞生于 2008 年, 它把 Git 仓库搬上网, 又加上了主页, star, fork, issue, 贡献图这些社交属性, 其中 Pull Request 是它的发明, 不是 Git 的功能.
- Git 是工具, 免费开源不属于任何人; GitHub 是托管这个工具产物的网站, 属于一家公司. 同类还有 GitLab, Bitbucket, Codeberg, 换平台不用重学.
- GitHub 的免费额度是一笔算得清的生意: 个人是入口, 企业才付费, 人多本身就是护城河.
- GitHub 的构造是作品加社交, 不是代码加社交. 作品有地方放, 而且自带认可, 关注和一条伪造不了的时间线, 所以它对不写代码的人同样是作品与职场的敲门砖.
- 用好它的三条: 当默认工作区, 能公开就公开, 但敏感内容一定 private, 且别把它当唯一副本.

## 14. 导师寄语

**为什么这一节值得读:**

这门课后面全是操作, 而操作是最容易学也最容易忘的东西. 真正能跟着你走很多年的, 是两样别的东西: 一是判断力, 知道什么是底层的, 什么是某一家公司的产品, 什么换了平台也带得走; 二是资格感, 知道自己有没有必要站在这块舞台上.

第二样我尤其想强调. 我见过太多不搞技术的人, 明明每天都在产出实实在在的东西, 却因为 "GitHub 是程序员的地方" 这一个念头, 把自己挡在门外, 于是这些年做过的东西全散在本地文件夹和邮件附件里, 想拿出来给人看的时候, 一件像样的都找不出来. 这不是能力问题, 是入场券问题, 而这张入场券本来是免费的.

**关键洞见:**

- 分清 "工具" 和 "平台", 是所有技术判断力的起点. Git 是工具, GitHub 是平台; 这个区分方式在别的领域同样成立.
- 免费的东西不是没有代价的, 只是代价不由你付. 想清楚谁在付, 你就知道这份免费能靠多久.
- 一个项目最好的备份不是某个网站的承诺, 而是它散落在很多人电脑上的那些完整副本. 这正是 Git 当初的设计目标之一.
- 别人相信你, 靠的不是你怎么描述自己, 而是你能拿出什么让他自己去看. 把作品放在一个公开, 带时间戳, 可点进去的地方, 是成本最低的一种自证.

**下一步:**

带着这两段故事和这个立场往下走. 下一节你就要亲手建第一个 repo 了, 到那时你会知道自己在做的事情是: 用一个 2005 年为了救急而写出来的工具, 在一个 2008 年建起来的广场上, 圈出属于你自己的一小块地方, 而这块地方将来是给别人看的.

## 15. 速查

**Git:** 2005 年 Linus Torvalds 写的分布式版本控制工具, 免费开源, 装在本地, 管的是改动历史, 眼里只有文本.

**GitHub:** 2008 年上线的 Git 仓库托管网站, 2018 年被 Microsoft 以 75 亿美元收购, 管的是仓库放在哪, 谁能看谁能改, 以及别人怎么看见它.

**一句话区分:** Git 管历史, GitHub 管这份历史放在哪, 谁能一起干活, 以及别人怎么看见它.

**Pull Request:** GitHub 的发明, 不是 Git 的功能. 后面会专门学.

**同类平台:** GitLab, Bitbucket, Codeberg. 底下都是同一个 Git, 换平台不用重学.

**免费档大致给了什么:** 不限量的 public 与 private 仓库, private 也能邀请协作者, 自动化额度, 静态网站托管, 学生与教师优惠. 具体数字年年变, 用时去 Pricing 页面看.

**它凭什么是敲门砖:** repo 放作品, README 当门面, star 和 follow 是社交认可, 贡献图是伪造不了的时间线. 这套东西不挑行业, 只要你的产出能落成文本.

**两条边界:** 别把 GitHub 当唯一副本 (本地 clone 就是完整备份); 敏感内容一律 private, 大文件和素材放别处留链接.
